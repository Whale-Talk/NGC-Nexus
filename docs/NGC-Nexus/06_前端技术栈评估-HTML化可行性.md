# QGC 前端技术栈评估：能否改为 HTML、放弃 Qt？

- 评估对象：QGroundControl `mavlink/qgroundcontrol`，HEAD `25185047e855937d694a0174c1541d8f7d794a74`
- 本地源码：`15_NGC-Nexus/repo`
- 方法：源码级实测统计（本机无 Qt6/MSVC，未编译）
- 结论口径：所有数字为实测；架构判断基于实测事实推导，标注"由源码推断"

---

## 0. 直接结论

**技术上可行，但"完全放弃 Qt"＝放弃 QGC，等于从零写一个地面站，不是"改前端"。**

关键区分：

| 说法 | 实际含义 | 工作量 |
|---|---|---|
| "把 QGC 前端换成 HTML" | 保留 C++ 业务逻辑，替换 UI 层 | 可行，重大重构 |
| "完全放弃 Qt 技术栈" | Qt 也是**运行时**（事件循环、对象模型、串口、蓝牙、定位、视频、主循环），不只是 UI 工具包 | 等于重写整个地面站 |

**推荐路线**：不要追求"去 Qt"，而是把目标定为**"UI 层去 QML，换 Web 技术"**，并分阶段推进。见 §5。

---

## 1. 实测事实

### 1.1 代码规模

| 层 | 文件数 | 行数 |
|---|---|---|
| QML（UI 层） | 478 | **57,273** |
| C/C++（业务逻辑层） | 1304 | **193,082** |

**C++ 是 QML 的 3.4 倍。** 换前端触及的只是那 27% 的展示代码。

### 1.2 QML 与 C++ 的绑定密度

| 宏/机制 | 出现次数 | 含义 |
|---|---|---|
| `Q_PROPERTY` | 1272 | 每个都是 QML 可读写的绑定点 |
| `QObject` | 1188 | 业务类全部是 QObject，依赖元对象系统 |
| `Q_INVOKABLE` | 469 | QML 可直接调用的 C++ 方法 |
| `QML_ELEMENT` | 116 | 注册为 QML 类型的类 |
| `QQmlEngine` | 35 | QML 引擎生命周期管理 |

QML 页面不是"独立的 HTML 式文档"，而是**深度绑定在 C++ 对象上**：
每个参数控件都直接绑定一个 `Fact` 对象的 `Q_PROPERTY`。把 QML 换成 HTML，等于要把这 1272 + 469 个绑定点重新定义一遍接口。

### 1.3 Qt 承担的不只是 UI

| Qt 能力 | 使用规模 | 换成 Web 后谁来干 |
|---|---|---|
| `QSerialPort`（串口链路） | **50 个文件** | 无 Web 等价物 → 必须原生桥 |
| QML 场景图渲染 | `QtQuick` 29 处 | 浏览器渲染（可行） |
| 地图 | `QtLocation` 12 处 | MapLibre / Leaflet（可行，但要重做离线高程与地形） |
| 视频 | `VideoManager` + GStreamer | WebRTC / MSE（UAV 低延迟图传是硬骨头） |
| 事件循环 / 应用骨架 | `main.cc` + `QGCApplication` | Electron/Tauri 或自建后端进程 |
| 平台抽象 | `deploy/` 六套（Win/Linux/macOS/Android/iOS/Docker） | 每个平台各自打包 |

全仓 **无任何 WebSocket / HTTP 服务端代码**（`QWebSocketServer`、`QHttpServer` 在 QML/C++ 侧零命中）。
但**框架层已有可用能力**：`CMakeLists.txt:252-279` 把 `HttpServer` 列为 **REQUIRED** 组件（同批还有 `Qml`、`Quick`、`QuickControls2`、`Location`、`Multimedia`、`Sensors`、`Sql`、`Quick3D`、`StateMachine` 等）。
即：Qt6 的嵌入式 HTTP 服务端**已在构建依赖里**，只是业务代码没用起来——这是"后端 + Web 前端"路线的一个现成立足点，可省掉引入新依赖的成本。

同时注意：**`WebEngine` / `WebView` 均不在组件清单中**，全仓 `QtWebView|QtWebEngine|WebView` 零命中——路线 B（WebView 混合）需要**新增 Qt 模块**，会带来部署体积与许可（WebEngine 基于 Chromium）的连带影响。

### 1.4 目标平台

`deploy/` 覆盖：Windows、Linux、macOS、**Android**、**iOS**、Docker。
QGC 是跨桌面与移动的地面站。HTML 方案在移动端要靠 WebView/WebKit 打包，且**离线地图、串口、摇杆、图传**这些无人机核心能力都要重新做原生桥。

## 2. 为什么"完全放弃 Qt"不成立

Qt 在 QGC 里是**四层叠加**的身份：

1. **UI 工具包**（QML/Qt Quick）—— 这一层可以换；
2. **对象模型与信号槽**（QObject/Q_PROPERTY/Q_INVOKABLE）—— C++ 业务逻辑的骨架，换掉等于重写 C++；
3. **平台抽象层**（串口、蓝牙、定位、文件、网络）—— Web 侧没有等价物，必须原生；
4. **应用运行时**（事件循环、主窗口、生命周期）—— 需要新的宿主进程。

**"只换第 1 层"是可行的重构；"把 1–4 全换掉"就是新项目。**

再叠加一个现实约束：**Web 前端本身也需要一个原生宿主**（Electron/Tauri/WebView），所以"完全放弃 Qt"实际是"用另一个原生框架替换 Qt"，并没有变成纯 Web —— 只是把 Qt 的 4 个身份换成 Chromium + Node/Rust + 原生桥。

## 3. 三条可行路线的对比

### 路线 A：后端化 —— QGC C++ 核心 + 独立 Web 前端

把 QGC 改造为**无界面后端进程**，对外暴露 WebSocket / REST（内部仍用 Qt Core 跑 MAVLink 与 Fact System），HTML 前端单独开发。

| 维度 | 评估 |
|---|---|
| 保留 | MAVLink 栈、参数系统、任务规划、地形、多机管理——全部成熟逻辑 |
| 新增工作 | 通信层（`Qt6 HttpServer` 已在依赖中，可直接用 → 成本低于预期）+ 1272/469 个绑定点的接口设计 + 前端从零写 |
| 前端自由度 | **最高**：任何框架、任何 UI 库、浏览器调试 |
| 硬难点 | 图传（GStreamer → WebRTC/MSE，低延迟是难点）、离线地图与高程、串口/摇杆原生桥、移动端打包 |
| 工作量 | **3–6 个月起**（单人） |
| 风险 | 中高：新增进程间协议本身成为新的复杂源与故障点 |

### 路线 B：混合 —— 保留 Qt 宿主，局部 WebView/Web 组件

仍用 QGC 现有架构，把**个别页面**（如参数页、遥测仪表盘）换成 Web 组件（QML `WebView` 或独立窗口）。

| 维度 | 评估 |
|---|---|
| 保留 | 全部现有能力，风险最小 |
| 新增工作 | 桥接层（把 Fact 暴露成 JSON/WS 给 Web 组件） |
| 前端自由度 | 局部：只有被替换的页面 |
| 工作量 | **2–4 周**（打通一个页面验证） |
| 风险 | 低 |
| 缺点 | QGC 本体仍需 Qt 构建（本机当前缺 Qt6/MSVC） |

### 路线 C：全部重写（Rust/TS + Tauri/Electron）

从零实现地面站，不再依赖 QGC。

| 维度 | 评估 |
|---|---|
| 工作量 | **年**级，且要重新实现 MAVLink 栈、参数系统、任务协议、地形、图传 |
| 收益 | 技术栈现代、可维护性好 |
| 风险 | **极高**：QGC 的成熟度是多年积累的结果，重写等于放弃它 |

## 4. 换前端会失去什么（必须正面回答）

| 能力 | 现状 | Web 化后的代价 |
|---|---|---|
| 低延迟图传 | GStreamer 管线，桌面/移动均可用 | 需 WebRTC；延迟与稳定性要重新验证 |
| 离线地图与地形高程 | QtLocation + 地形数据 + 高程查询 | 需重做，数据格式与缓存策略全部重来 |
| 串口/蓝牙遥测 | `QSerialPort` 50 处、蓝牙链路 | 浏览器无法直接访问 → 必须原生桥 |
| 摇杆输入 | Qt 输入抽象 | 需 Gamepad API 或原生桥 |
| 移动端（Android/iOS） | 现成部署链 | WebView 打包 + 原生桥，等于重做一遍 |
| 单一代码库跨 6 平台 | `deploy/` 已就绪 | 各平台分别维护宿主 |

## 5. 建议路线（分阶段，可随时停）

### 阶段 0：先拿到"看得见的好用"（**建议立刻做**）

不换技术栈，直接修 QGC 现有前端的 4 个实证缺陷。**收益/成本比最高**：

| 缺陷 | 证据位置 | 改动量 |
|---|---|---|
| 写入成功无任何反馈 | `ParameterManager.cc` 成功分支只写日志 | 小 |
| 搜索不匹配枚举文本 | `ParameterEditorController.cc:718,725` | 小 |
| 参数页排序两处下标误用 | `ParameterEditorController.cc:241-265` | 小 |
| 生成式页控件推断未生效 | `control_renderers.py:374` | 中 |

前置条件：装 Qt 6 + MSVC（当前缺失）。

### 阶段 1：验证 Web 前端可行性（**2–4 周**）

按路线 B 做一个**垂直切片**：选**参数页**（最独立、数据结构最清晰）做 Web 版。

为什么选参数页：它只依赖 `Fact` 的 name/value/unit/enum 等有限字段，不碰地图、视频、任务协议——是**验证"Fact → JSON → HTML"通路的最佳试点**。

### 阶段 2：决定是否全面转向（**基于阶段 1 的实测**）

阶段 1 会暴露真实成本（桥接复杂度、刷新率、交互延迟、打包难度）。拿到这些数字后再决定：

- 若桥接清爽、体验达标 → 按路线 A 逐页迁移；
- 若别扭 → 停在路线 B，用 Web 只做局部增强；
- **不建议**路线 C。
