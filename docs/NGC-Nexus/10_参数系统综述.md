## 0. 结论速览

| 问题 | 结论 |
|---|---|
| QGC 前端显示参数的唯一通路是什么 | **Fact System**。所有参数与遥测都变成 `Fact` 对象，QML 只见 Fact，不直接碰 MAVLink。上游 `AGENTS.md` 把这条列为不可违反的架构铁律 |
| 参数值怎么来 | MAVLink `PARAM_VALUE`（标准参数协议），全量请求有三条路径：PX4 哈希校验缓存握手 → MAVFTP 取 `param.pck` → `PARAM_REQUEST_LIST` |
| 参数**元数据**怎么来 | **两家完全不同的机制**：PX4 走 Component Information（MAVFTP 取 `parameters.json.xz`）；ArduPilot 走**编译期外置的 JSON 参数定义**（`ArduPilot/ParameterRepository` 的 `apm.pdef.json`，QGC 构建时下载并打进 Qt 资源）。**两者的 `PARAM_EXT_*` 均与整车参数显示无关** |
| 元数据怎么映射到显示 | 元数据 → `FactMetaData` → 驱动 `Fact` 的 QML 属性 → 参数页按 `category`/`group` 分组、按类型选控件 |
| 前端改造的关键切入点是哪一处 | `CompInfoParam::_resolveMetaData()`（`src/Vehicle/ComponentInformation/CompInfoParam.cc:88`）—— **两家的元数据在这个函数汇合**，是唯一改动点 |

## 1. 基座：QGC 是如何被构建出来的

`src/` 下 32 个一级模块、1303 个 C/C++ 文件（226953 行）、478 个 QML 文件（66772 行）。

QML 根入口（`src/API/QGCCorePlugin.cc:315`）：

```cpp
qmlEngine->load(QUrl("qrc:/qml/QGroundControl/MainWindow.qml"));
```

与技术栈相关的三条事实：

1. 依赖不靠 git 子模块。本仓库**没有 `.gitmodules`**，顶层也没有 `libs/`。依赖走三条路径：外部 Qt（`cmake/presets/Windows.json:10` 的 `$penv{QT_ROOT_DIR}`）、CPM 下载（缓存目录 `.cache/CPM`，实测不存在）、GStreamer SDK 下载。
2. QML 类型注册用 `QML_ELEMENT` / `QML_SINGLETON` 等宏，全仓 280 处命中、分布 21 个模块；源码树内**没有** `qmldir` / `*.qmltypes`，均构建期生成。
3. `MAVLinkEnums.h` 是构建期产物（生成器 `tools/generators/mavlink_enums.py`，规则 `src/MAVLink/CMakeLists.txt:64-83`），源码树中不存在。

## 2. 参数从飞控到屏幕的完整通路

### 2.1 报文层：谁把字节变成消息

```
LinkInterface::bytesReceived（UDP/TCP/Serial/Bluetooth/LogReplay/Mock）
  └─> LinkManager.cc:194   接到 MAVLinkProtocol::receiveBytes
        └─> MAVLinkProtocol.cc:102 组帧、:115 mavlink_parse_char、:294 emit messageReceived
              └─> Vehicle.cc:525 _mavlinkMessageReceived（sysid 过滤 → 插件预处理 → 分发）
                    └─> Vehicle.cc:577 _parameterManager->mavlinkMessageReceived
```

注意一个容易搞错的点：**`MAVLinkProtocol` 在 `src/Comms/`，不在 `src/MAVLink/`**。`src/MAVLink/` 只放消息类型、FTP、图像、状态文本、签名、事件库。

### 2.2 参数层：`ParameterManager`

`src/FactSystem/ParameterManager.cc:107` 是整车 `PARAM_VALUE` 的**唯一**处理点。要点：

- 收到后解码（`:111`），手工补 `param_id` 的 `\0` 终止符（`:114-116`，MAVLink 不保证终止）。
- 若正在走 FTP 参数文件路径，则丢弃流式 `PARAM_VALUE`（`:120-123`）。
- 全量请求三条路径：PX4 `_HASH_CHECK` 缓存握手 → MAVFTP `param.pck` → `PARAM_REQUEST_LIST`。
- 超时/重试常量集中在 `src/FactSystem/ParameterManager.h:111-124`：`PARAM_SET` 重试 2 次、初始请求 4 次、单索引 5 次、批在飞上限 10、静默 2 轮后放弃非默认组件。
- **元数据请求先于参数请求**：`InitialConnectStateMachine.cc:188-190` 的状态序为 AutopilotVersion → StandardModes → **CompInfo** → **Parameters**。这保证了建 Fact 时元数据已经就绪。

> 历史沿革提示：`ParameterLoader` 这个类在本 HEAD **已不存在**（`src/FactSystem/` 无该类，CMake 清单也没有），仅在 `docs/` 开发指南里留有文字残留。现存的等价角色就是 `ParameterManager`，它同时承担加载器与仓库两职。

### 2.3 Fact 层：一个参数变成 Fact 的瞬间

`ParameterManager.cc:250` 在**首个 `PARAM_VALUE` 到达时**创建 Fact，紧随其后（`:251-252`）挂接元数据：

```
ParameterManager::_handleParamValue
  ├─> CompInfoParam::factMetaDataForName(...)   // 取元数据
  ├─> Fact::setMetaData(...)
  └─> Fact::containerSetRawValue(value)         // 设值 → 触发 QML 绑定
```

因此不存在"先渲染出无名参数、再补元数据"的空窗。

### 2.4 写回：`PARAM_SET` 状态机

```
Fact::setRawValue → emit containerRawValueChanged
  └─> ParameterManager::_factRawValueUpdated (:536)
        └─> ParameterManager::_mavlinkParamSet (:306) → PARAM_SET → 等应答
```

`ParameterEditorController` 是**纯视图模型**，不持有存储；它因 `ParameterManager.h:30` 的 `friend` 声明而可直接调用私有的 `_mavlinkParamSet`（`src/QmlControls/ParameterEditorController.cc:418`）。

## 3. 关键分叉：PX4 与 ArduPilot 的元数据来源完全不同

这是本次梳理**最重要的结论**，也是前端改造必须先理解的一层。

### 3.1 汇合点：一个函数裁决三元来源

`src/Vehicle/ComponentInformation/CompInfoParam.cc:88-112` 的 `_resolveMetaData()` 按 `_noJsonMetadata` 标志分流：

```cpp
FactMetaData *CompInfoParam::_resolveMetaData(const QString &name, FactMetaData::ValueType_t valueType)
{
    if (_noJsonMetadata) {
        // No vehicle-provided metadata — use firmware-bundled metadata
        if (ParameterMetaData *fwMeta = _getParameterMetaData()) {
            return fwMeta->getMetaDataForFact(name, valueType);      // ← APM 走这条
        }
    } else {
        // Vehicle provided JSON metadata — check exact match then indexed patterns
        if (FactMetaData *found = _lookupJsonMetaData(name)) {
            return found;                                            // ← PX4 走这条
        }
    }

    // Generic fallback：按第一个下划线前缀设 group
    auto *factMetaData = new FactMetaData(valueType, this);
    const int sep = name.indexOf('_');
    if (sep > 0) { factMetaData->setGroup(name.left(sep)); }
    if (compId != MAV_COMP_ID_AUTOPILOT1) { factMetaData->setCategory(tr("Component %1").arg(compId)); }
    return factMetaData;
}
```

`_noJsonMetadata` 默认 `true`（`CompInfoParam.h:31`），即**默认走固件内置元数据路径**，只有确认车端提供了 JSON 元数据才切到 `_lookupJsonMetaData`。这条分流决定了 PX4 与 ArduPilot 在 QGC 里走完全不同的元数据通路。

| 分支 | 来源 | 适用 |
|---|---|---|
| `!_noJsonMetadata` → `_lookupJsonMetaData` | 车端 component information JSON | 支持该协议的固件（PX4） |
| `_noJsonMetadata` → `_getParameterMetaData()` | 固件相关元数据提供者 | ArduPilot 等不支持该协议的固件 |
| 兜底 | `new FactMetaData(valueType)` + 按下划线前缀猜 group | 两边都没有时 |

**前端改造要动参数呈现，这里就是唯一的分流点。**

### 3.2 PX4 侧：编译期生成 + Component Information 分发

PX4 v1.18 的参数定义方式已经变了：**全仓库已无手写 `PARAM_DEFINE_FLOAT/INT32`**，定义源全部迁到 `src/modules/*/module.yaml` 与 `params_*.yaml`（实测：直接用 PX4 自带 stdlib-only 的 srcscanner/srcparser 扫描 `src/` 得到 **0 个参数**，反证扫描输入必须是构建期产物）。

生成链路：

```
69 个 module.yaml + 33 个 params*.yaml
  └─> Tools/module_config/generate_params.py  → module_params.c / serial_params.c
        └─> px_process_params.py（scanner 非递归）→ parameters.xml / parameters.json (+xz)
              └─> px_generate_params.py → px4_parameters.hpp
```

（各步 CMake 规则见 `src/lib/parameters/CMakeLists.txt:40,65-67,79-90,111-152`）

元数据的三条出路（**三者并存**）：

| 方式 | 说明 |
|---|---|
| 编译进固件并嵌 ROMFS | 默认路径，`kconfig.cmake:307-317` |
| 完全外置到 S3 | 板卡开 `CONFIG_BOARD_EXTERNAL_METADATA=y` 时（`Kconfig:113`，当前 4 块板卡） |
| 运行期生成 | 仅 peripheral 元数据（`common.xml:8173`） |

交给地面站的方式是 **Component Information**（不是 `PARAM_EXT_*`）：

```
MAV_CMD_REQUEST_MESSAGE(512, param1=397) → COMPONENT_METADATA
  → 给出 mftp://etc/extras/component_general.json.xz + CRC
    → MAVFTP 取 parameters.json.xz
```

证据：`COMPONENT_METADATA.hpp:50-74`、`mavlink_receiver.cpp:913-956`、`mavlink_ftp.h:195-196`。

> **负面结论（对前端很重要）**：PX4 **完全不用 `PARAM_EXT_*`**（值通道 320-324 之外无实现）；且本版 MAVLink 中**没有 `MAV_COMP_ID_PARAMETER` 这个常量**（零命中检索）。

### 3.3 ArduPilot 侧：元数据来自构建期外置的 JSON，不是运行时推送

任务初始假设是"APM 元数据随 `PARAM_VALUE`/`PARAM_EXT_VALUE` 推送"，**该说法不成立**，有三条独立证据：

1. MAVLink 官方文档明确 `PARAM_EXT_*` 是为相机协议发明、飞行栈普遍不支持（[parameter_ext.html](https://mavlink.io/en/services/parameter_ext.html)）。
2. ArduPilot 自己发布的 Copter-4.7 MAVLink 支持表把 5 条 `PARAM_EXT_*` 全标为 `UNSUPPORTED`，`COMPONENT_INFORMATION`/`COMPONENT_METADATA` **零命中**（[MAVLinkMessages.rst](https://github.com/ArduPilot/ParameterRepository/blob/main/Copter-4.7/MAVLinkMessages.rst)）。
3. QGC 侧 `PARAM_EXT_*` 只出现在相机子系统（`QGCCameraIO.cc`、`VehicleCameraControl.cc`）；且 QGC 自己写了注释 "ArduPilot doesn't support the component metadata protocol"（`RequestMetaDataTypeStateMachine.cc:441`）。

真实链路：

```
ArduPilot 源码参数定义
  └─> param_parse.py（编译/发布期）→ apm.pdef.json → ArduPilot/ParameterRepository
        └─> QGC 构建期用 CPM 拉取 → 打进 Qt 资源
              → :/FirmwarePlugin/APM/APMParameterFactMetaData.<Vehicle>.<Maj>.<Min>.json
```

证据：`src/FirmwarePlugin/APM/APMFirmwarePlugin.cc:710`（读取点）、`src/FirmwarePlugin/APM/CMakeLists.txt:41-114`（打包规则，`:69` 为关键行）。全仓 `pdef` **无任何运行时下载代码**，本仓库内也**没有** APM 元数据文件本体，全部来自外部依赖。

随 `param.pck?withdefaults=1` 下来的**只是默认值**（`ParameterManager.cc:690`），写入 `setRawDefaultValueFirmwareForce`（`FactMetaData.cc:165`）—— 那是默认值，不是元数据。

实测 `Copter-4.7/apm.pdef.json`（2229014 字节）：顶层 387 个组、字段名只有 12 个。**发现两个 QGC 未消费的字段：`Volatile` 与 `Calibration`** —— `APMParameterMetaData::_lookupMetaData` 不读它们；而 PX4 侧对 volatile 参数会强制只读（`PX4ParameterMetaData.cc:67-69`）。

### 3.4 两家差异对照（节选）

| 差异项 | PX4 | ArduPilot | QGC 处理位置 |
|---|---|---|---|
| 元数据来源 | Component Information，MAVFTP 运行时取 | 构建期打包进 Qt 资源 | `CompInfoParam.cc:88-112` |
| 元数据形态 | `parameters.json.xz`（含 min/max/unit/enum/bitmask/reboot） | `apm.pdef.json` | 同上 + `APMFirmwarePlugin.cc:710` |
| `PARAM_EXT_*` | 不支持 | 不支持（相机专用） | 与整车参数无交集 |
| volatile 参数 | 强制只读 | 字段存在但 QGC 未消费 | `PX4ParameterMetaData.cc:67-69` |
| 默认值获取 | 随元数据 | `param.pck?withdefaults=1` | `ParameterManager.cc:690` |

完整 13 项对照表与 13 条适配点见分册 `05_APM参数系统对照.md`。

## 4. 元数据怎么映射到显示

### 4.1 分组与搜索

- 一级分组用 `category`、二级用 `group`（`ParameterEditorController.cc:194-212`）。
- 搜索**只匹配 name / shortDesc / longDesc**（`:717-727`），**不含枚举文本与位掩码显示文本**；300 ms 去抖、空格为 AND 语义。
- 元数据缺失时：category 落 `Other`（APM 为 `Advanced`、PX4 为 `Standard`），group 落 `Misc`。

### 4.2 类型 → 控件（三条不同路径）

| 路径 | 位置 | 规则 |
|---|---|---|
| 手写参数页 | `ActuatorFact.qml:48-51` | 逐个控件手写 |
| 生成式参数页 | `control_renderers.py:350-362` | 按 `control` 键查表，**缺省回落文本框** |
| 设置页自动推断 | `emit.py:109-161` | 真正按元数据自动推断 |

### 4.3 单位与小数位

raw / cooked 双域：内置换算表 + 应用设置表；`decimalPlaces()` 三级推导（`increment` 优先 → 3 位兜底，夹在 [0,25]）。

### 4.4 边界与降级行为

- 越界：统一文案、红框 + Tooltip、可恢复原值；**非法值不写入且阻止切换视图**（`MainWindow.qml:122-132`）；Force save 仅高级 UI 可见。
- 只读：锁图标，三处呈现。
- 枚举缺文本：注入 `Unknown: <值>`。
- 位掩码空选中：显示上游原文 `Not value selected`。

## 6. 必须声明的边界与未验证项

1. **本机无法编译 QGC**：无 Qt6、无 MSVC。所有 UI 表现类结论均为源码推断，未实机验证。
2. **PX4 元数据生成未实跑完整链路**：本机缺 pyyaml / jinja2 / jsonschema，且未获授权装包。已用 PX4 自带 stdlib-only 组件实跑得到真实 JSON/XML 产物，但"参数总条目数"等需要完整生成才能给出的数字**未提供**。
3. **PX4 侧两条源码不一致（已复核，影响待定）**：
   - `src/lib/parameters/CMakeLists.txt:124` 引用的 schema 路径 `mavlink/component_information/parameter.schema.json` **不存在**（实际在 `component_metadata/`），配合 `--skip-if-no-schema` 使 JSON 校验在本版本**实际不生效**。
   - `jsonout.py:10` 写 `version = 1`，而 schema 要求 `version >= 3`；XML 侧写 3（`xmlout.py:24`），两者口径不一致。
   - **边界声明：QGC 对该 `version` 字段的实际容忍度未验证**，不能把"校验被跳过"外推为"前端一定不受影响"。
4. **浅克隆限制**：分析基于 `depth=1` 克隆，无法给出某类/某字段的历史删除时点（例如 `ParameterLoader` 的移除时间）。
5. **`AppSettings` 是二义名**：C++ 类在 `src/Settings/AppSettings.h:9`；`src/AppSettings/` 是纯 QML 设置界面模块（0 个 `.h`/`.cc`）。后续任务书需指明所指。
6. **一处源码不一致（非本次任务范围）**：`src/FactSystem/FactControls/` 磁盘上有 18 个 `.qml`，但 `CMakeLists.txt` 的 `QML_FILES` 只登记 17 个 —— `FactTextFieldRow.qml` 未注册，不会进入 QML 模块资源。原因未验证。
7. **两处死代码/能力不对称（已记录）**：`_loadMetaData/_clearMetaData/_tryCacheLookup` 是头文件死声明（无定义无调用）；`_mavlinkParamUnionToVariant` 不支持 `REAL64/UINT64/INT64`，而类型映射表支持。
