## 0. 结论摘要

| 参数定义写在哪里 | **全部在 YAML**（`src/modules/*/module.yaml`、`params_*.yaml` 等），源码树中已无手写 `PARAM_DEFINE_*` | `Tools/module_config/generate_params.py:153-161`；全仓库检索 `PARAM_DEFINE_FLOAT`/`PARAM_DEFINE_INT32` 仅命中 `docs/**` 与 `Tools/serial/serial_params.c.jinja:42,69` |

## 1. 全链路总览

```
[A] 定义源（YAML，随源码提交）
    src/modules/<mod>/module.yaml + params_*.yaml
        │  CMake 注册：set_property(GLOBAL APPEND PROPERTY PX4_MODULE_CONFIG_FILES ...)
        │              （cmake/px4_add_module.cmake:253；读取处 src/lib/parameters/CMakeLists.txt:40）
        ▼
[B] YAML → C 源码（构建期）
    Tools/module_config/generate_params.py  →  ${PX4_BINARY_DIR}/generated_params/module_params.c
    Tools/serial/generate_config.py         →  ${PX4_BINARY_DIR}/generated_params/serial_params.c
        │  （src/lib/parameters/CMakeLists.txt:65-95）
        ▼
[C] 扫描 + 注解解析（构建期）
    src/lib/parameters/px_process_params.py
      ├─ px4params/srcscanner.py：对 --src-path 目录内 *.h、*.c 逐个扫描（**非递归**）
      └─ px4params/srcparser.py：解析 doc 注释标签 @group/@min/@max/@unit/@decimal/@value/@bit/
                                  @boolean/@reboot_required/@category/@volatile/@board
        ├──▶ parameters.xml   （中间格式，xmlout.py）
        ├──▶ parameters.json  （地面站元数据，jsonout.py）→ parameters.json.xz
        └──▶ parameters.json.xz 是 component_general.json 的输入之一
        ▼
[D] XML → 固件头文件（构建期）
    src/lib/parameters/px_generate_params.py + templates/px4_parameters.hpp.jinja
      → px4_parameters.hpp：enum class px4::params{...}、parameters[]（name+默认值）、
                             parameters_type[]、parameters_volatile[]、parameters_readonly[]
        ▼
[E] 编入固件（运行期）
    src/lib/parameters/parameters.cpp + parameters_common.cpp：param_find/param_get/param_set、
    ConstLayer/DynamicSparseLayer 分层存储、parameter_update uORB 通知、autosave 落盘
        ▼
[F] MAVLink 值通道（运行期）
    src/modules/mavlink/mavlink_parameters.cpp：
      PARAM_REQUEST_LIST/READ/SET → param_find/param_get/param_set → PARAM_VALUE(n)/PARAM_ERROR
        ▼
[G] MAVLink 元数据通道（运行期）
    COMPONENT_METADATA/COMPONENT_INFORMATION 给出 URI+CRC → MAVLink FTP 取
    mftp://etc/extras/component_general.json.xz → 其内 metadataTypes[type=1].uri
    → mftp://etc/extras/parameters.json.xz（或 S3 回退 URL）
```

地面站侧对 `PARAM_VALUE`/`PARAM_ERROR` 的消费链路见同目录 `03_QGC参数链路.md`；本文只负责 PX4 侧给出什么、以什么形式给出。

## 3. 元数据在系统里的存法：注解 → 生成物 → 运行时结构

### 3.1 注解标签全集（源码即元数据源头）

`px4params/srcparser.py:198`：

```
valid_tags = {"group","board","min","max","unit","decimal","increment",
              "reboot_required","value","boolean","bit","category","volatile"}
```

解析规则：`@value <code> <描述>` 进枚举表（`:252-255`）、`@bit <index> <描述>` 进位掩码表（`:256-259`）、其余进通用字段表（`:260-261`）；作用到参数对象见 `:327-344`。参数名/类型/默认值来自紧随其后的 C 定义（`:300-313`，正则 `:191-196`）。

同一批标签在 YAML 侧的名字略有不同（YAML 用 `values:`/`bit:`/`decimal:` 等结构化写法），由 `Tools/module_config/generate_params.py` 翻译成 `@` 注解：

- `@group`：`:108`（来自 `group:` 段落名）
- `@value`：enum 类型 `:111-112`，float 带 values 时 `:127-129`
- `@bit` 与自动 `@min 0`/`@max (1<<(max_bit+1))-1`：`:113-119`
- `@boolean`：`:120-122`
- `@decimal/@increment/@category/@volatile/@min/@max/@unit/@reboot_required`：`:133-136`
- 最终输出形如 `PARAM_DEFINE_{FLOAT|INT32}({name}, {default});`：`:153-161`

### 3.2 生成物 1：`px4_parameters.hpp`（**编译进固件的那一份**）

模板 `src/lib/parameters/templates/px4_parameters.hpp.jinja` 只渲染五样东西：

| 内容 | 行号 |
|---|---|
| `enum class params : uint16_t { ... }`（参数名 → 编译期句柄枚举） | `:11-21` |
| `static constexpr param_info_s parameters[]`（**只有 name 与默认值**） | `:23-34` |
| `static constexpr param_type_t parameters_type[]` | `:36-40` |
| `static constexpr params parameters_volatile[]` | `:42-48` |
| `static constexpr params parameters_readonly[]` | `:50-56` |

因此固件内的"参数元数据"实际只有：**名字、类型、默认值、是否 volatile、是否 readonly**。`min/max/unit/decimal/increment/enum/category/reboot_required/bitmask/shortDesc/longDesc` **一个都不进固件**。运行时结构对应 `src/lib/parameters/param.h:500-503`：

```c
struct param_info_s {
    const char *name;
    union param_value_u val;   // param.h:489-492 的 i/f 联合
};
```

对 `src/lib/parameters/*.cpp/*.h` 检索 `min|max|unit|decimal|reboot|bitmask|category`，除测试文件与注释外无任何运行时字段命中——这是"元数据不进固件"的直接反证。

| `@bit` | `bitmask: [{index,description}]` | `:131-138` |

JSON 的结构由 MAVLink 侧的 schema 定义：`src/modules/mavlink/mavlink/component_metadata/parameter.schema.json`（`name:23-28`、`type:29-33`、`units:46-51`、`min:63-67`、`max:68-72`、`rebootRequired:77-81`、`category:87-91`、`values:97-111`、`bitmask:112-125`、`readOnly:126-130`、`additionalProperties:false` `:133`、顶层必填 `["version","parameters"]` `:137`）。

`translation` 段（`jsonout.py:14-38`）声明了哪些字段可被翻译文件覆盖（`shortDesc`/`longDesc`/`category`/`group`，以及 `values`/`bitmask` 的描述），对应的翻译文件 URI 由构建期写入 `component_general.json` 的 `translationUri`（见 §4.4）。

### 3.6 关键判断题：编译进固件 / 运行期生成 / 外部文件

三者在同一套机制里各占一段，**不是三选一**：

1. **编译进固件（默认分支）**
   - 值/类型/默认值/volatile/readonly：编译期进 `px4_parameters.hpp`（§3.2）。
   - 富元数据：编译期生成 `parameters.json`，打成 `parameters.json.xz` 后由 `cmake/kconfig.cmake:307-317` 加入 ROMFS（条件是 `NOT CONSTRAINED_FLASH AND NOT EXTERNAL_METADATA`，且板卡 label 非 `test`）。
   - 运行期固件自身**不解析**该 JSON；它只是被 FTP 当普通文件读出去。

2. **外部文件（受限 flash 板卡分支）**
   - `Kconfig:113` 提供 `BOARD_EXTERNAL_METADATA`；本仓库置 `=y` 的板卡有 `boards/espressif/esp32/default.px4board:4`、`boards/diatone/mamba-f405-mk2/default.px4board:6`、`boards/ark/cannode/default.px4board:6`、`boards/holybro/kakutef7/default.px4board:5`。
   - 此时 ROMFS 不嵌入 JSON；`component_information/CMakeLists.txt:45-50` 改为给出 S3 上的 URI（`https://px4-travis.s3.amazonaws.com/Firmware/{version}/<vendor>_<model>_<label>/parameters.json.xz`）与 `_general` 回退 URI。
   - 另有 `PARAM_DEFAULT_OVERRIDES`（CMake 变量，默认 `"{}"`，`src/lib/parameters/CMakeLists.txt:36-38,119`）用于在构建时改默认值；本仓库没有任何板卡设置该变量，即默认分支不使用它。
   - `readonly_params.yaml`（板卡级，`src/lib/parameters/CMakeLists.txt:101-109`）本仓库中不存在任何一份（`boards/**/readonly_params.yaml` 检索零命中），但生成器与运行时都已具备该能力（`readonly_config.py:17-48`、`px4_parameters.hpp.jinja:50-56`，运行期上锁见 §3.3）。

3. **运行期生成（局部）**
   - 只有外设类元数据是运行期生成的：官方消息定义明确写 `COMP_METADATA_TYPE_PERIPHERALS` 的 URI"must be generated dynamically at runtime"（`common.xml:8173`）。PX4 侧 `COMPONENT_INFORMATION` 报文中该字段留空（`streams/COMPONENT_INFORMATION.hpp:64-69` 只填 general URI 与 CRC）。
   - 参数值本身当然是运行期的（`param_get` 读的是 RAM/Flash 中的当前值，`parameters.cpp:297-366`），但**值不属于元数据**。

## 4. 地面站取参数值：协议细节

### 4.1 全量拉取

1. 地面站发 `PARAM_REQUEST_LIST`(21)（`common.xml:5611`）。
2. PX4 校验 `target_system`/`target_component`（`mavlink_parameters.cpp:156-157`，允许 `MAV_COMP_ID_ALL`），置 `_send_all_index = PARAM_HASH`（`:158-164`；第二次请求则直接置 0，跳过哈希）。
3. 发送循环在接收线程里被周期驱动：`_parameters_manager.send()`（`mavlink_receiver.cpp:3971`），每次最多 3 个（串口非 USB）或 20 个（USB/UDP），并受发送缓冲与电台状态限制（`mavlink_parameters.cpp:438-452`）。
4. 第一条 `PARAM_VALUE` 是**哈希哨兵**：`param_id = "_HASH_CHECK"`（`mavlink_main.h:94`）、`param_type = MAV_PARAM_TYPE_UINT32`、`param_index = -1`、`param_count = param_count_used()`、`param_value` = `param_hash_check()`（`mavlink_parameters.cpp:544-562`；哈希算法 `parameters.cpp:1367-1385`）。
5. 之后逐条发送 **used 参数**（跳过未使用与 `PARAM_INVALID`，`:564-585`），每条 `PARAM_VALUE` 含名字、类型、当前值、`param_count`、`param_index`（`:603-681`）。
6. 地面站命中缓存时，可以直接发 `PARAM_SET`(`param_id="_HASH_CHECK"`)，PX4 收到即停止发送全量并回 `MAV_PARAM_ERROR_READ_ONLY`（`mavlink_parameters.cpp:200-211`）。该"哈希命中即停"的开关由 `MAV_HASH_CHK_EN` 控制（`mavlink_main.h:480`；参数定义 `src/modules/mavlink/mavlink_params.yaml:81-88`）。

要点：**`used` 语义决定地面站能看到多少参数**。`param_find()`/`param_find_no_notification()` 之外的读取路径都会标记 used（`param.h:283-288` 的注释、`parameters.cpp:207-209`、`:535-548`）。PX4 在 `MavlinkParametersManager::send()` 首次调用时主动 `param_find()` 一批"地面站不能容忍缺失"的参数（`mavlink_parameters.cpp:409-436`），其中包含 `SENS_BOARD_ROT`(`:424`)、`SENS_DPRES_OFF`(`:428`)、`SYS_PARAM_VER`(`:433`)。

### 4.4 Component Information 通道（元数据）

1. 地面站发 `MAV_CMD_REQUEST_MESSAGE`(512)，`param1 = 397`（`common.xml:2138`；`COMPONENT_METADATA` ID 见 `:8186`）。

### 4.5 组件 ID 与目标过滤

- PX4 的 `mavlink_system` 静态初值为 sysid=1、compid=1（`src/modules/mavlink/mavlink.c:49-52`），随后被 `MAV_SYS_ID`/`MAV_COMP_ID` 参数覆盖（参数默认值同样是 1，`src/modules/mavlink/mavlink_params.yaml:5-20`）；构造 `Mavlink` 实例时一次性锁存（`mavlink_main.cpp:202-229`，注释 `:205-211`）。`mavlink_bridge_header.h:74-75` 里的 `sysid=100/compid=50` 只是注释中的示例写法，不是实际取值。

- 本版本 MAVLink 定义中**没有** `MAV_COMP_ID_PARAMETER`；参数服务不存在独立组件号。若地面站要区分参数来源，只能按 compid（自动驾驶仪 vs 相机 vs CAN 节点）区分。

### 5.4 实跑中发现的两处不一致（供 QGC 侧注意）

2. **version 口径不一致**：`jsonout.py:10` 写 `version = 1`（实测输出亦为 1），而 `parameter.schema.json:8-11` 要求 `version >= 3`；XML 输出侧写的是 3（`xmlout.py:24`）。若日后修复 (1) 使校验生效，JSON 会立刻校验失败。地面站对该字段的容忍度需在 QGC 侧另行核实（本次未验证 QGC 行为）。

## 6. 参数实例：从定义源头追到 MAVLink 发出

下述链路中，"MAVLink 发出"均指两件事：**值**经 `PARAM_VALUE`（`mavlink_parameters.cpp:590-686`），**元数据**经 `parameters.json` → FTP（§4.4）。

### 6.1 实例一：`EKF2_GPS_P_NOISE`（float，带 min/max/unit/decimal）

### 6.3 实例三：`SENS_BOARD_ROT`（enum + `reboot_required` + 被 MAVLink 侧强制标记 used）

| 步骤 | 位置 | 内容 |
|---|---|---|
| 定义 | `src/modules/sensors/sensor_params.yaml:74-125` | `type: enum`，`values: 0..40` 共 41 项（`:80-121`），`default: 0`（`:122`），`min: -1`（`:123`），`max: 40`（`:124`），`reboot_required: true`（`:125`） |
| 生成 C | `generate_params.py:109-112,133-136,161` | 每个枚举值一行 `@value <code> <描述>`，外加 `@reboot_required true` |
| 扫描解析 | `srcparser.py:252-255,341-344` | `@value` 进 `SetEnumValue`，在 XML/JSON 中输出为 `values` 列表（实测 JSON 见 §5.3） |
| 固件头 | `px4_parameters.hpp.jinja:36-40` | 映射为 `PARAM_TYPE_INT32`（enum 在 YAML 侧就是 int32，`generate_params.py:109-110`） |
| 强制 used | `mavlink_parameters.cpp:409-436` | `send()` 首次调用即 `param_find("SENS_BOARD_ROT")`（`:424`），确保其出现在全量参数列表中 |

### 6.4 实例四：`EKF2_GPS_CTRL`（bitmask → JSON `bitmask`）

| 步骤 | 位置 | 内容 |

## 7. 对 QGC 二次开发的接口要点

1. **值走消息、元数据走文件**：`PARAM_VALUE` 只有名字/类型/值/计数/索引（`common.xml:5616-5622`）；描述、单位、min/max、枚举、bitmask、`rebootRequired`、`category` 全部来自 `parameters.json`。任何"在 UI 上补齐参数信息"的需求都必须以 Component Information + MAVFTP 为前提；拿不到 JSON 时地面站只能显示裸名字。
2. **`param_count`/`param_index` 是"used 列表"口径**：`param_count_used()`（`parameters.cpp:239-242`）与 `param_get_used_index()`（`:266`），与固件总参数个数（`param_count()`，`parameters_common.cpp:53-56`）不同。UI 若把索引当全局下标会错位。
3. **`_HASH_CHECK` 是协议内的加速机制**，不是参数；名字固定 `"_HASH_CHECK"`（`mavlink_main.h:94`），写它会被回 `MAV_PARAM_ERROR_READ_ONLY`（`mavlink_parameters.cpp:200-211`）。同时 `MAV_HASH_CHK_EN` 可被用户关掉（`mavlink_params.yaml:81-88`），此时 PX4 会持续推送变化参数（`mavlink_parameters.cpp:476-525`）。
4. **写入确认与错误**：每次成功 `PARAM_SET` 都会回一条 `PARAM_VALUE`（`:234-236`）；错误走 `PARAM_ERROR`(345, WIP)（`:689-741`），其中 `MAV_PARAM_ERROR_READ_ONLY` 只在只读锁生效后出现：`param_is_readonly()` 在 `param_lock_readonly()` 之前恒为 false（`parameters_common.cpp:99-117`），而该锁由启动脚本的 `param lock` 在开机流程末尾调用（`ROMFS/px4fmu_common/init.d/rcS:749-752`；命令实现 `src/systemcmds/param/param.cpp:452-453`）。地面站的重试/回滚逻辑必须同时处理这两类回包。
5. **元数据可以是"外链"**：`component_general.json` 的每个 `metadataTypes` 条目都带 `uriFallback`（受限 flash 板卡或 S3 分发场景，`component_information/CMakeLists.txt:45-53`），并可能带 `translationUri`（翻译文件在 GitHub 上，`:56`）。UI 需要按"主 URI 失败→回退 URI"的顺序取，且要容忍 `fileCrc` 变化后的重新下载（CRC 由 `generate_crc.py:49-51` 以 MAVLink CRC32 计算）。
6. **`version` 字段的坑**：见 §5.4——本版本 JSON 写 1、schema 要求 ≥3、校验被跳过。若 QGC 侧对该字段做严格校验/分支，需自行决定策略。
7. **每板卡一套元数据**：`--board ${PX4_BOARD}` 影响 board 专属参数是否保留（`xmlout.py:53-59`、`jsonout.py:91-97`），因此同一固件版本不同板卡的 JSON 并不等价；做参数界面时不能硬编码某一板卡的参数全集。

## 9. 边界与未验证声明

1. 本文所有结论仅对本节开头给出的两个提交（PX4 `6dc89338…`、mavlink 子模块 `1b1e896…`）成立。PX4 参数体系在近几个版本重构频繁（YAML 化、`src/systemcmds/param` 取代 `src/modules/param`、primary/remote 拆分、`param_info_s` 精简），差异版本不可套用。

3. §5.3 实验 B 的输入是**按生成器模板构造的片段**，不是真实构建产物；其价值在于验证 PX4 自带 parser/输出器的行为与字段形状，不能替代真实 `module_params.c` 的统计结论。
4. 地面站（QGC）侧如何消费这些报文与 JSON（含对 §5.4 两处不一致的处理）不在本文范围；对应分析见 `03_QGC参数链路.md` 与 `04_参数到界面映射.md`。
5. `PARAM_ERROR` 与 `MAV_PARAM_ERROR` 在本 MAVLink 版本中标记为 WIP（`common.xml:2912-2913,7950-7951`），其语义与取值可能随上游变化。
6. 本地改造版 `PX4-H1` 未纳入分析；其参数差异（新增/改名/默认值）不能引用本文结论，需要单独比对。
